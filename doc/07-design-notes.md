# 07 — Design notes

## 1. Behaviours worth knowing

| Behaviour                                                                                                                                                                                  | Consequence                                                                                                                                  |
|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------|
| A plan belongs to one pull request at a time: when an event is received, the repository's plans are assigned to the most recent PR and older PRs are left without plans.                    | `ci:rerun` flows fall back to the plans of the repository. Changing this would require an association table.                                  |
| Finishing a stage (`success`, `failure`, `cancelled`) creates a fresh check run and concludes it; `Stage#enqueue` also creates a new one.                                                   | The previous check run for the stage stays in GitHub's history.                                                                              |
| Only stages have check runs; CI jobs are audited but call GitHub only if they have a `check_ref`.                                                                                          | The GitHub checks tab shows one entry per stage, not per job.                                                                                |
| A re-requested check suite creates the new suite without linking the plan (`plan_id` is NULL).                                                                                             | The copy is identified by its commit and Bamboo reference.                                                                                    |
| Retry looks up the stage by its check run name (without the multi-plan suffix).                                                                                                            | Naming of stages must stay stable for `ci:retry` to find them.                                                                               |
| A late `success` callback for a job that was already `cancelled` is accepted; only `queued` and `in_progress` jobs have the 304 guard.                                                      | Results reported late by Bamboo are not lost.                                                                                                |
| Topotest failure fetching gives up after more than 3 attempts, even if failures were still reported.                                                                                       | The delay grows between attempts (5 x n minutes); after the limit the result is discarded.                                                   |
| `ci:retry` and `ci:rerun` in the same comment: `retry` wins.                                                                                                                               | Only the failed work is requeued.                                                                                                            |
| Execution time uses the first `in_progress` and the first `success`/`failure` audit entry.                                                                                                 | Re-executions accumulate in the total.                                                                                                       |
| `ci:rerun #sha` runs the unavailable-jobs step over all suites of the same commit and moves missing jobs to the new suite; whitespace around the sha is ignored.                           | Jobs removed from the Bamboo plan are marked skipped in the old suites.                                                                      |
| PR lookup for `ci:retry`/`ci:rerun` also filters by repository when it is known.                                                                                                           | Two repositories with the same PR number do not get mixed up.                                                                                |
| The execution timeout falls back to the suite's `updated_at` when the suite has no jobs, and the finished-execution lookup only uses the keys provided.                                   | A suite without a Bamboo reference is never picked by mistake.                                                                               |
| Without plans configured for the repository a pull request event returns 422; there is no default plan.                                                                                    | Configure plans before enabling the App on a repository.                                                                                     |
| `debug` and other settings are read at start-up.                                                                                                                                           | Restart the services after changing configuration.                                                                                           |
| `CI_URL` accepts a host or a URL and always produces `https://host/browse/...` links.                                                                                                      | No doubled scheme in Bamboo links.                                                                                                           |

## 2. Robustness decisions

| Decision                                                                                                                                  | Reason                                                                                                   |
|-------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|
| Installation token cache and renewal; JWT with a back-dated `iat`; a `401` renews the token                                               | Avoids creating a JWT and token for every check call (hundreds per execution).                           |
| Bounded retries: reads and PATCH on transient failures, any method on rate limit or `Retry-After`; no POST retry after a network error    | Resilience without repeating non-idempotent effects.                                                     |
| Jobs that start a plan in Bamboo (`create_execution_by_*`) have `max_attempts = 1`                                                         | A late failure must not start several plans.                                                             |
| Advisory lock per PR in the creation and cancellation flows                                                                               | Rapid events on the same PR cannot cancel or create concurrent executions.                               |
| Auxiliary failures do not abort the flow: comment reactions, GitHub user lookup, Slack notifications                                      | A failing side channel must not break PR processing.                                                     |
| `Finished` answers `503` and changes nothing when Bamboo is unavailable                                                                   | State is never reconciled from missing data; the watch dog retries later.                                |
| Webhook authentication runs before JSON parsing; invalid JSON returns `400`; a missing `X-GitHub-Event` returns `400`                      | Unauthenticated callers never reach the parser.                                                          |
| Secrets never reach the logs (pattern-based redaction); the Bamboo submission URL is not logged; headers and environment are not dumped   | The URL carries the signature secret.                                                                    |
| XML escaping of comments sent to Bamboo; query strings encoded by the HTTP client                                                         | Prevents malformed or injected content.                                                                  |
| `output.summary` limited to 65,535 characters                                                                                             | GitHub rejects larger summaries with 422.                                                                |
| Check runs listed with `per_page=100`                                                                                                     | Avoids stopping at the first page.                                                                       |
| Incomplete PR or payload data returns `422` instead of creating invalid records                                                           | Fail early with a clear status.                                                                          |
| Optional deduplication by `X-GitHub-Delivery` (`WEBHOOK_DEDUPE_TTL_SECONDS`, off by default)                                              | GitHub's Redeliver button reuses the delivery id, so it stays opt-in.                                    |
| `GET /healthz`, `GET /readyz` (checks the database), `/ping`; `/telemetry` with version, uptime and pool state                            | Health checks for systemd, Ansible and load balancers.                                                   |
| TLS defaults: Slack bot verified (`SLACK_BOT_VERIFY_TLS=true`); Bamboo not verified (`BAMBOO_VERIFY_TLS=false`, loopback by default)      | Set `SLACK_BOT_VERIFY_TLS=false` only for a self-signed bot certificate; enable Bamboo verification for remote hosts. |
| File logs with `WatchedFileHandler` plus logrotate; per-PR log files; journald only when `netdef_ci_file_logging` is false               | Several processes write the same files.                                                                  |
| Workers per queue range, managed by systemd                                                                                               | Updates for one PR are serialized by `github_pr_id % 10` queues; named queues have their own worker.     |
| systemd timers for `watch-dog` (every 15 minutes) and `pr-bamboo-sync` (hourly)                                                           | `Persistent=true`, logs in the journal, controlled by Ansible.                                           |
| The watch dog isolates failures per suite                                                                                                 | One broken suite does not stop reconciliation of the others.                                             |

## 3. Metrics notes

| Metric                                                                                                                       | Notes                                                                                           |
|------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------|
| `delayed_jobs_pending`, `delayed_jobs_running`, `delayed_jobs_scheduled`, `delayed_jobs_failed`, `delayed_jobs_max_attempts_reached`, `delayed_jobs_locked_too_long`          | Gauges labelled by `queue`, computed from the `jobs` table at scrape time.                       |
| `delayed_jobs_table`                                                                                                                 | Per-job scheduled timestamp, for inspecting what is queued.                                      |
| `activerecord_queries_total`, `activerecord_query_duration_seconds`                                                                              | Labelled by `operation` and `table`; `table` is the SQL table name (for example `ci_jobs`).      |
| `activerecord_connection_pool_size`, `activerecord_connection_pool_connections`, `activerecord_connection_pool_busy`, `activerecord_connection_pool_idle`            | Connection pool state.                                                                           |
| `ci_jobs_total{status}`, `ci_job_timeout_total`, `app_exceptions_total`, `bamboo_api_requests_total`, `github_api_requests_total`, `slack_notifications_total` | CI state and integration health.                                          |

| `puma_workers_total`, `puma_booted_workers` | Configured (`WEB_WORKERS`) and currently running web worker processes. |
| `puma_running_threads`, `puma_pool_capacity`, `puma_max_threads`, `puma_backlog` | Simplified per-worker saturation, labelled by `worker` (pid): requests in flight, free slots, the worker thread-pool size (40) and a `puma_backlog` that is always 0 because uvicorn does not expose its queue. |
| `http_server_requests_total{code,method,path}`, `http_server_request_duration_seconds`, `http_server_exceptions_total` | Request counters/histogram by route pattern, and exceptions by class. |
| `activerecord_connection_pool_waiting` | Always 0: SQLAlchemy's pool does not expose its waiters. |

Dashboards and alert rules must use these names and the `table` label. Metric files of dead worker processes are cleaned up automatically (`test_stale_metric_files_of_dead_processes_are_removed`).
